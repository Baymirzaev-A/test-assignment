## 1. Underlay: eBGP по connected-стыкам, а не по loopback'ам


**eBGP по /31-стыкам (connected):**
1) Соответствует RFC 7938 - стандартное решение, 
2) Конфиг проще (нет статики и multihop), легче масштабируется. Сначала я планировал делать по loopback, но передумал. Если бы изначально я планировал ebgp по стыкам, то выбрал бы сетки /30, по-моему так было бы "чище".

### Overlay

Loopback VTEP (`10.10.10.X`) анонсируется в underlay через `network` в BGP, чтобы все узлы знали, как до него добраться. Это единственная роль loopback'ов в underlay — они не участвуют в установлении BGP-сессий, но должны быть доступны для VXLAN-туннелей.

| Компонент | ASN |
|-----------|-----|

Одна общая AS для overlay. Spine'ы — Route Reflector'ы для iBGP EVPN. Сессии — по loopback'ам VTEP (`10.10.10.X`). Выбор 64999 (вне диапазона underlay-AS) сделан для визуального разделения underlay и overlay в конфигах и диагностике.

## 4. MLAG vs EVPN Multihoming

По условию задания обязательно применение обоих вариантов подключения.

Для evpn mh создается общий ES (**ETHERNET SEGMENT**), он объединяет физические подключения одного сервера к двум leaf, у нас ES 1001 (это идентификатор) на лиф 1 и 2 и ES 1002 на лиф 3 и 4.
EVPN MH, работает напрямую через оверлэй, сообщения тип 1 и 4.

**Тип 1** - используется для объявления информации о ES, благодаря ему VTEP знают о доступности ES

**Тип 4** - нужен для обнаружения всех участников одного ES, для DF election.


**ES system mac** - общий мак, для идентификации общего ES.

То есть он должен совпадать на утсройствах одного сегмента.

**DF election**, DF - это лиф, который ответственен за передачу BUM трафика в сторону ES, чтобы сервер не получал дублирующие пакеты. Но в пересылке обычного юникаст участвуют оба. 
 
 Можно задать Preference, чтобы гарантировать победу конкретного leaf, у нас будут DF leaf 1 и 3 (200 priority)

Еще есть такое понятие, как EVI (EVPN Instance) - это по сути MAC-VRF
### MLAG на frr проблема, нейронка предложила python mlagd
**Что делает демон**

При запуске он задат параметры:
 - ad_actor_system - общий мак пары, общий LACP system ID
 - ad_actor_sys_prio - приоритет sys id, равен 100
 - ad_user_port_key - 101/102

Соответсственно , оба коммутатора из заданной пары представляются одинм маком, и сервер может объединить два интерфейса (порты 1 и 2) и мы видим это в проверке в ранбук (**Проверка LACP на Leaf**)

Каждый leaf отправляет UDP-пакет своему соседу (heartbeat), интервал 1 секунда, таймаут 3 секунды, отпраялется на VTEP_IP через андерлэй.

peer link реализован через порт eth3, наш демон ***не передает*** через него таблицы mac, lacp состояние и VLAN.
 Но при этом реализованы три состояния:
 1) DAD и peer-link есть, тогда оба коммутатора active
 2) heartbeat пакеты теряются, тогда secondary блокается
 3) peer link down, тогда тоже secondary блокается

Так мы защищаемся от DUAL active.

ГЛавное, что надо релизовывать - **синхронизация MAC/FDB**, то есть если сервак отправляет кадр через leaf 1, лиф вносит запись в мак таблицу, но второй leaf этой записи не получает.
